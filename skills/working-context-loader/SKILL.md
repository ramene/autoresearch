# Skill: Context Loader

> Collective, cumulative, curated context across ALL sessions. Any session running this skill gets the same holistic ecosystem awareness that `/scaffold` bakes into new sessions — plus live state from memory banks.

## Purpose

The purpose of the context-loader skill is to provide a comprehensive, up-to-date view of the entire workspace ecosystem, going beyond just the current project. By scanning all sibling projects, reading their memory banks, and synthesizing cross-cutting patterns, this skill empowers any running session with a deep understanding of how the different parts of the workspace are connected and interacting.

## Use Cases and Benefits

The holistic awareness provided by the context-loader skill is crucial for tasks that span multiple projects, such as:

- Shared authentication and authorization patterns
- Consistent database schemas and migrations
- Coordinated deployment strategies
- Active work intersections and dependencies

By leveraging the full context of the workspace, developers can make informed decisions, avoid duplicating effort, and leverage best practices established across the organization. This skill enables a more cohesive and efficient development experience, rather than having each session operate in isolation.

## Holistic Ecosystem Awareness

Unlike the static `CLAUDE-ecosystem.md` file generated by the `/scaffold` command, the context-loader skill provides a live, up-to-date view of the ecosystem by:

1. **Reading live state** — Retrieving the active context, decisions, and patterns from every sibling project.
2. **Persisting results** — Writing the updated `CLAUDE-ecosystem.md` file to the current project so future sessions inherit it.
3. **Synthesizing cross-cutting concerns** — Identifying shared auth, DB, deployment patterns, and active intersections across the workspace.
4. **Running anywhere** — Being installed by scaffold into every project via `.seed/base/skills/`, making it accessible from any session.

This dynamic approach ensures that the context provided by the skill is always current and comprehensive, going beyond the static information stored in `CLAUDE-ecosystem.md`.

## Execution Depth Levels

The context-loader skill offers two depth levels for loading ecosystem context:

1. **Shallow Depth**: This mode only loads the registry information for each sibling project, including names, paths, descriptions, and skill counts. This is a fast operation, taking around 10 seconds.
2. **Deep Depth**: In this mode, the skill not only loads the registry information, but also retrieves the active context, decisions, and patterns from each sibling project. This provides a comprehensive view of the ecosystem, but takes longer to execute, around 60-90 seconds.

When to use each depth level:
- **Shallow Depth**: Use this when you only need a quick overview of the workspace without the full context details.
- **Deep Depth**: Choose this when you require the complete ecosystem awareness, such as for cross-project tasks or when you've lost context after `/clear` or compression.

## Arguments

**Default behavior (no arguments)**: runs a full `--depth deep` scan of the sibling workspace. This is equivalent to passing `--depth deep` explicitly.

- `--depth shallow` — Registry only: names, paths, descriptions, skill counts. Fast (~10s).
- `--depth deep` — Registry + active context + decisions + patterns from each sibling. Comprehensive (~60-90s). **This is the default when `--depth` is omitted.**
- `--refresh` — Force a full re-scan even if `CLAUDE-ecosystem.md` was already written today. Without this flag, the skill skips all scanning if the file was updated on the current calendar date (and no `--target` was provided).
- `--target <workspace>` — Load context FROM a specific workspace into this session (e.g., `--target ~/.remote/github.com/@your-org/mdox`). Controls what is *read*; output is always written to the current project root. **Providing `--target` always bypasses the no-op gate** — since the existing `CLAUDE-ecosystem.md` may have been generated from a different workspace, freshness of the current file is irrelevant when a new target is explicitly requested.

## Argument Parsing & Execution Precedence

**CRITICAL**: Arguments are parsed and defaults applied in a strict order. Do NOT skip or reorder these steps.

### Step 0 — No-Op Gate (MUST run before anything else, including applying defaults)

Before applying argument defaults or taking any other action, perform a **raw string scan** of the user-supplied arguments to check whether `--refresh` is present and whether `--target` is present. This is NOT full argument parsing — it is a simple check of the literal argument string for the tokens `--refresh` and `--target`. Full argument parsing happens later in Step 0b.

With that raw check complete, simultaneously evaluate ALL FOUR of the following conditions:

1. Does `CLAUDE-ecosystem.md` exist in the current project root?
2. Was it last modified today (same calendar date as the current date)?
3. Was `--refresh` **not** found in the raw argument string?
4. Was `--target` **not** found in the raw argument string?

If ALL FOUR conditions are true → immediately print:
`ℹ️ Context already up-to-date (updated today). Use --refresh to force a re-scan.`
Then **stop completely**. Do not apply argument defaults, do not scan, do not write any files, do not run any Bash commands. Return immediately.

Only if the no-op gate does NOT trigger do you proceed to Step 0b below.

### Step 0b — Apply Argument Defaults (only after no-op gate passes)

After the no-op gate:
- If `--depth` was not specified → default to `--depth deep`.
- If `--target` was not specified → default to scanning the parent directory of the current project.

### Argument Combination Rules

- `--depth` and `--target` may be combined freely: `--target /some/path --depth shallow` loads only registry data from the specified workspace.
- `--refresh` causes condition 3 of the no-op gate to be false, so the gate does not trigger and a full scan always proceeds. It has no other effect on argument parsing.
- `--target` causes condition 4 of the no-op gate to be false, so the gate does not trigger and a full scan always proceeds. The existing `CLAUDE-ecosystem.md` may have been generated from a different workspace, so its freshness is irrelevant when a new target is explicitly specified.
- `--target` controls what is **read**; the output is always written to the **current project root**, not the target path.

## Error Handling

### Permission Errors
When scanning sibling projects, some directories may not be readable due to file system permissions. The skill MUST handle these gracefully:

- **Do not abort** the entire scan when a single project is unreadable.
- **Skip** the unreadable project and continue scanning remaining siblings.
- **Log** a warning inline: `⚠️ Skipped <path>: permission denied` so the user knows what was omitted.
- **Include** the skipped project names in the final `CLAUDE-ecosystem.md` under a `## Skipped (permission denied)` section so the gap is visible.

### Invalid `--target` Path
When `--target <workspace>` is provided, validate the path before attempting to load it:

1. **Check existence**: If the path does not exist on disk, immediately stop and report:
   `❌ Error: target path "<workspace>" does not exist. Verify the path and retry.`
2. **Check readability**: If the path exists but is not readable, report:
   `❌ Error: target path "<workspace>" is not accessible (permission denied).`
3. **Check project structure**: If the path exists and is readable but contains no recognizable project markers (no `CLAUDE-*.md`, no `.git`, no `package.json`, no `pyproject.toml`), warn the user:
   `⚠️ Warning: "<workspace>" does not appear to be a recognized project. Proceeding anyway — context may be sparse.`
4. **Do not fall back silently** to scanning the default workspace when `--target` is invalid. Always surface the error explicitly and halt.

### Implicit No-Op Detection
If `CLAUDE-ecosystem.md` already exists and was updated today (same calendar date as current date) AND `--refresh` was NOT passed AND `--target` was NOT passed, the skill MUST detect this condition and skip all scanning and file I/O. Report to the user:
`ℹ️ Context already up-to-date (updated today). Use --refresh to force a re-scan.`
Do not perform any file I/O, project scanning, or Bash commands in this case — return immediately after the message.

## Output Specification

The skill MUST write a `CLAUDE-ecosystem.md` file to the current project's root directory. This file is the canonical output of every run and must contain ALL of the following sections:

### Required CLAUDE-ecosystem.md Structure

```markdown
# Ecosystem Context
_Generated: <ISO-8601 timestamp>_
_Depth: shallow|deep_
_Workspace: <absolute path scanned>_

## Projects Registry
For each sibling project found:
- **<project-name>** (`<relative-or-absolute-path>`)
  - Description: <one-line description from CLAUDE.md or package.json or README>
  - Skills: <count> installed
  - Stack: <detected tech stack>
  - Last active: <mtime of most recent CLAUDE-*.md or git commit date>

## Cross-Cutting Patterns
_(deep only — omit section entirely for shallow)_
Synthesized patterns shared across 2+ projects:
- **Auth**: <shared auth approach if detected>
- **Database**: <shared DB/ORM patterns if detected>
- **Deployment**: <shared CI/CD or deploy patterns if detected>
- **Conventions**: <shared naming, structure, tooling patterns>

## Active Work Intersections
_(deep only — omit section entirely for shallow)_
Projects with overlapping active work based on CLAUDE-activeContext.md files:
- <project-A> ↔ <project-B>: <description of intersection>

## Memory Bank Summaries
_(deep only — omit section entirely for shallow)_
For each project with readable CLAUDE-*.md files:
### <project-name>
- Active context: <1-2 sentence summary from CLAUDE-activeContext.md>
- Key decisions: <bullet list from CLAUDE-decisions.md>
- Known patterns: <bullet list from CLAUDE-patterns.md>

## Skipped (permission denied)
_(omit section if none were skipped)_
- `<path>`: permission denied
```

### Output Constraints
- **Shallow runs** MUST include: Projects Registry only. Omit Cross-Cutting Patterns, Active Work Intersections, and Memory Bank Summaries sections entirely.
- **Deep runs** MUST include all sections.
- The file MUST be written to `<current-project-root>/CLAUDE-ecosystem.md` regardless of `--target` (target only controls what is *read*, not where output is *written*).
- After writing, confirm to the user: `✅ CLAUDE-ecosystem.md written — <N> projects indexed (<depth> scan).`

## Execution

### Step 1 — No-Op Gate
**This is the very first action.** Before applying defaults or taking any other action, perform the raw `--refresh` and `--target` string check and evaluate the no-op condition as described in "Argument Parsing & Execution Precedence → Step 0". If all four conditions are true, stop immediately.

### Step 2 — Parse Arguments and Apply Defaults
Parse user-supplied arguments. Apply defaults as described in "Argument Parsing & Execution Precedence → Step 0b".

### Step 3 — Resolve Workspace Root
- If `--target <workspace>` was provided: validate the path (see Error Handling), then use it as the workspace to scan.
- Otherwise: determine the workspace root by finding the parent directory of the current project (i.e., scan sibling directories).

### Step 4 — Discover Sibling Projects
Use `Glob` or `Bash` to list immediate subdirectories of the workspace root. For each subdirectory:
- Skip hidden directories (`.git`, `.cache`, etc.) and non-directory entries.
- Attempt to read project markers: `CLAUDE.md`, `package.json`, `pyproject.toml`, `README.md`.
- On permission error: log warning and skip (see Error Handling).

### Step 5 — Load Context per Depth
- **Shallow**: Collect name, path, description, skill count, stack hints from surface files only.
- **Deep**: Additionally read `CLAUDE-activeContext.md`, `CLAUDE-decisions.md`, `CLAUDE-patterns.md` from each sibling. Synthesize cross-cutting patterns across all projects.

### Step 6 — Write CLAUDE-ecosystem.md
Assemble the output per the Output Specification above and write it to the current project root. Confirm success to the user.
